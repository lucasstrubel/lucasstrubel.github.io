5 DAX Patterns Every Power BI Developer Should Know

Power BI DAX Data Analytics Tutorial

Introduction

DAX (Data Analysis Expressions) is the formula language that powers Power BI. At first glance it looks a lot like Excel — familiar functions, a spreadsheet mindset. But DAX operates on tables and relationships, not cells, which means the mental model is fundamentally different. Once that clicks, a whole set of patterns becomes available to you.

This post covers five patterns I reach for constantly when building dashboards. They are not obscure — they are the building blocks that unlock dynamic calculations, proper filtering, and clean, maintainable measures.

1. CALCULATE — The Most Important Function in DAX

CALCULATE evaluates an expression in a modified filter context. Nearly every non-trivial DAX measure uses it, directly or indirectly. 

Sales YTD =
CALCULATE(
    SUM(Sales[Amount]),
    DATESYTD(Calendar[Date])
)

The first argument is the expression to evaluate. Every argument after that is a filter modifier. Here, DATESYTD replaces the calendar filter with all dates from the start of the year up to the current date. The key insight: CALCULATE does not add filters — it replaces existing ones when there is a conflict, and adds new ones otherwise.

Understanding this distinction is what separates DAX beginners from intermediate practitioners. If your measure is returning unexpected totals or ignoring slicers, the answer is almost always a misunderstood CALCULATE context transition.

2. ALL and ALLEXCEPT — Escaping the Filter Context

Sometimes you need a calculation that ignores one or more of the active filters — typically to compute a percentage of total or a ratio against a fixed baseline. 

% of Total Sales =
DIVIDE(
    SUM(Sales[Amount]),
    CALCULATE(SUM(Sales[Amount]), ALL(Sales))
)

ALL(Sales) removes every filter on the Sales table, so the denominator is always the grand total regardless of which product, region, or date is selected.

ALLEXCEPT is the inverse — it removes all filters except the columns you specify. Useful when you want a category-level total that respects the category slicer but ignores subcategory selections: 

Category Total =
CALCULATE(
    SUM(Sales[Amount]),
    ALLEXCEPT(Products, Products[Category])
)

3. SUMX — Row-by-Row Iteration

DAX has two families of aggregation functions: the simple ones (SUM, COUNT, AVERAGE) and the iterator variants (SUMX, COUNTX, AVERAGEX). The iterators let you define a per-row expression before aggregating. 

Total Revenue =
SUMX(
    Sales,
    Sales[Quantity] * Sales[Unit Price]
)

This iterates over every row in the Sales table, multiplies Quantity by Unit Price for that row, then sums the results. You cannot do this with a plain SUM because SUM only operates on a single column. Whenever your calculation involves a row-level expression before aggregation, reach for an iterator.

Iterators are also essential for weighted averages and any measure where the "what" you aggregate changes per row.

4. Time Intelligence — DATEADD and SAMEPERIODLASTYEAR

Power BI's time intelligence functions require a proper date table marked as such, with no gaps and a continuous daily grain. Given that, period-over-period comparisons become straightforward. 

Sales LY =
CALCULATE(
    SUM(Sales[Amount]),
    SAMEPERIODLASTYEAR(Calendar[Date])
)

YoY Growth % =
DIVIDE(
    SUM(Sales[Amount]) - [Sales LY],
    [Sales LY]
)

SAMEPERIODLASTYEAR shifts the current date filter back exactly one year. DATEADD is more flexible — it shifts by any number of intervals (days, months, quarters, years) in either direction: 

Sales 3 Months Ago =
CALCULATE(
    SUM(Sales[Amount]),
    DATEADD(Calendar[Date], -3, MONTH)
)

Build your time intelligence measures in a logical sequence: base measure first, then prior-period variants, then ratios. This keeps the measure table readable and makes debugging much easier.

5. VAR — Readable, Reusable Intermediate Values

DAX variables, introduced with VAR ... RETURN, are one of the most underused features in practice. They let you compute an intermediate result once, give it a name, and reference it multiple times — without recalculating. 

Margin % =
VAR TotalRevenue = SUM(Sales[Amount])
VAR TotalCost    = SUM(Sales[Cost])
VAR GrossProfit  = TotalRevenue - TotalCost
RETURN
    DIVIDE(GrossProfit, TotalRevenue)

Without variables, you would either repeat the SUM expressions three times or create separate measures. Variables eliminate redundancy and make the logic easy to follow — even for someone reading your work months later.

Variables are also invaluable for debugging: comment out the RETURN line, replace it with RETURN TotalRevenue, and you can inspect any intermediate value directly in the visual.

Putting It Together

These five patterns compose naturally. A real-world measure might use VAR to define intermediate values, CALCULATE to modify context, ALL to escape a filter, and SUMX to iterate — all in the same expression. Once each pattern is familiar individually, combining them becomes intuitive.

The best way to internalize DAX is to write measures against a dataset you understand well, check the results at every step, and keep the filter context question in mind: what rows are visible when this expression evaluates? Answer that, and the pattern that fixes it becomes obvious.
